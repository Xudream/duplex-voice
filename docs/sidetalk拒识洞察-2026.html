1. 结论与成熟度

1.1 一句话结论

2026 年这个问题的性质变了：不再是"能不能检测旁对话"，而是"同一句话换个说话人，模型会不会闭嘴"。

现有证据给出的答案是——端到端音频大模型基本不会闭嘴（VGBench 上 6 个原生模型 + 3 种免训练适配，最高静默率仅 14%），

必须靠独立门控或专门后训练才能到 91%。

产品侧也不是没做，而是已经形成四层格局（见 §4，收录 28 个模型与产品）：模型层 12 个（GPT-Live、Gemini Live、Qwen-Audio-3.1-Realtime、Gander、Seeduplex、Step-Audio 2、GLM-Realtime 等）、

基础设施层 7 个（LiveKit 轮次检测、Pipecat Smart Turn v3、ElevenLabs、Deepgram、AssemblyAI、OpenAI semantic_vad、Silero）、

产品层 9 个（ChatGPT Voice、Gemini for Home、Alexa、Siri/Apple UAD、AirPods、Ray-Ban Meta、AI Pin、车机音区、Teams）。

只有阿里公开了 sidetalk 量化（背景语音响应 73%→13%），没有一家公开误拒率——这是我们对标时最缺的口径。

2. 术语与边界

2.1 拒识的四个子场景（HumDial 口径）【论文】

ICASSP 2026 HumDial Challenge 把 Track II 的拒识拆成四类：

缩写全称中文系统应有动作
URBuser real-time backchannels用户实时附和静默继续（不打断）
PHpause handling停顿处理等待，不抢话
TPSthird-party speech第三方在说话静默
SDOspeech directed at others对他人说的话（sidetalk）静默 + 记上下文

sidetalk ≈ SDO（主用户转向旁人），TPS 是它的相邻场景（背景里别人在聊，主用户没参与）。

2.2 三类"不该回应"的语音（VGBench 口径）【论文】

类型定义例子文本层是否可分
side-talk主用户对旁人说话"帮我把这个放桌上"（对同事）不可分（与指令同形）
self-talk自言自语"嗯……这个放哪来着"部分可分（无请求对象）
speaker-switch同一句话换说话人/距离/时间边界同一句指令由旁人说 vs 穿戴者说完全不可分

speaker-switch 是三者中最难的：词不变、只有来源变，任何纯文本模型都无能为力。

2.3 与现有 8 态 reject 的冲突（这是产品级问题）

现状：user_reject 定义为"听不清/不理解"，动作是澄清（"没听清，再说一遍"）。

冲突：sidetalk 场景下如果复用 user_reject，系统会对着一句对旁人说的话追问"没听清，再说一遍"——

这比不回应更糟。两者动作互斥：

状态触发动作动作方向
user_reject说了但没听清/听不懂澄清主动发话
sidetalk听清了，但不是说给系统静默 + 记上下文完全不发话

结论：不能复用，必须拆态。

3. 2026 年三个关键进展

3.1 问题被重定义：从分类到序列路由【论文】

SAS / SDAR（arXiv:2604.08412，2026-04）：

项内容
设定预 ASR、端上部署：决定"这段音频要不要送去转写"
核心主张多说话人 + 时间歧义下，应建模为基于交互历史的序列路由，而非逐句分类
结果（60h 多说话人英文测试集）纯音频 F1 0.86（P 0.89 / R 0.83）；加摄像头 F1 0.95（P 0.97 / R 0.93）
关键消融去掉因果交互历史：F1 从 0.95 掉到 0.57（±0.03）

含义：历史上下文是最大的单一信号，比声学特征更值钱。这对只有单麦的手机/耳机形态尤其重要。

3.2 端到端的失败被量化【论文】

VGBench（arXiv:2609.32536，2026-09）：

项内容
规模1,018 条诊断样本
覆盖side-talk / self-talk / speaker-switch
动作空间静默 / 调工具 / 正常回答（action-level addressedness）
关键设计speaker-switch 配对：词完全相同，只改来源、距离渲染、时间边界
主要发现6 个原生 Audio LLM + 3 种免训练适配：常能选对工具，但很少选择闭嘴；最高 switch 静默率仅 14%
后训练案例（VoxGate）监督训练后静默 switch 命令 91.3%；GRPO 阶段 side-talk 准确率 68.4% → 70.9%，self-talk 静默 52.0% → 60.0%

含义：sidetalk 失败不是"听不清"，而是"不愿意不回答"——这是训练目标问题，不是 ASR 精度问题。

来源规模与 sidetalk 的关系

4.6 结论：共性、分歧、空白与动作

三条共性

  • 都吃上一轮上下文：Alexa 的 DDSD 明确编码前一句；与 SAS 消融"去掉历史 F1 从 0.95 掉到 0.57"互证
  • 都有兜底动作：静默、让路、归属、轻确认——没有产品把"二分类硬判"当终点
  • "是否对设备说"与"是否说完了"是两个判断：OpenAI 的 turn_detection 只管说完，拒识靠模型或上层；阿里把两者合进 smart_turn

    • 两处必须选边的分歧

    分歧选项 A选项 B我们的选择
    判为旁人说之后静默让路（降音量）静默 + 可回看（我们是手机/耳机，让路会打断用户自己的播放）
    门控放哪训进模型（Gander / 阿里）参数 + 外挂（OpenAI、LiveKit、Pipecat）外挂门控 + 参数化契约（用云 API 没有权重）

    四个空白（产品侧真没人做好）

    空白说明对我们的含义
    sidetalk 长时态旁人连聊 30 秒以上如何重新锚定，无任何产品公开方案只能自建评测
    多人交替对系统说会议里 A、B 轮流提问行业仍靠唤醒词
    电视 / 儿童噪声Alexa 明说 TV 与小孩喊叫是最难负例负例集必须单列这两类
    误拒指标无一家公开误拒率，只报准确率或 EER自己定 FAR/FRR 工作点，否则无法对标

    四条动作

  • 判定输入补"上一轮 + 场景"：我们当前只看当前段音频，与所有玩家都不一致
  • 输出改三档（对设备说 / 旁人说 / 不确定），不确定走轻确认，不硬判
  • 把语义轮次与说话人锁定做成可替换接缝：与现有 VadJudge 同构，云 API 的 smart_turn、LiveKit 的 turn detector、Pipecat Smart Turn 可互换
  • 对标表补"误唤醒 / 误拒"口径：并加一条产品事故维度（Ray-Ban 2026-10 无唤醒词录音、AI Pin 关服）

    诊断CoDeTT（SMR）、VGBench（静默率）判断错在"没识别出"还是"识别了但不肯闭嘴"
    训练数据ChorusDuplex-SideTalk + 自建中文合成集只够跑通链路，上产品需补真实录音

    6. 已解决 vs 未解决

    6.1 一张表看清现状

    已解决未解决
    多通道/可穿戴的 sidetalk 拒识可用（93.9%，WearVox 案例研究口径）单通道（手机/耳机）只能到 F1 0.86 量级
    交互历史是强信号（消融 +38 点）端到端模型默认不肯静默（14%）
    评测能区分"为什么没说"（SMR）误拒的代价未被建模（把指令当 sidetalk 的惩罚）
    后训练可显著改善（91.3%）中文真实数据缺，现有为合成
    音视频融合可到 0.95sidetalk 持续性 / 结束后的重锚，无基准

    6.2 对选型的含义

    结论含义
    单通道上限约 F1 0.86手机/耳机形态不要按"零误判"设计，需要"轻确认"兜底
    端到端默认不肯静默静默能力必须由独立门控保证，不能指望模型自觉
    历史上下文是最大杠杆判定时必带最近 3–5 轮，单句判定注定不准
    中文真实数据缺自建数据是必选项，不是可选项

    7. 对 8 态 VAD 的改造建议

    7.1 状态表：8 态 → 10 态

    状态含义动作相对现状
    complete说完了回复不变
    incomplete没说完等待续说不变
    backchannel附和不打断、不应声不变
    noise环境音丢弃不变
    tts_echo回声忽略不变
    barge_in_intentional有意打断停播 + 接管不变
    barge_in_unintentional无意打断忽略不变
    user_reject听不清/听不懂澄清语义收窄（只保留"没听清"）
    sidetalk（新）对旁人说静默 + 记上下文新增，动作与 reject 相反
    self_talk（新）自言自语静默（可选：低置信时轻确认一次）新增

    7.2 判定信号优先级

    优先级信号来源说明
    1交互历史会话状态SAS 消融证明最大杠杆（+38 点）
    2称呼/第二人称ASR 文本"帮我/你/小X" vs 无称呼
    3说话人变化声纹/多通道方向单通道得不到，多通道可得
    4声学距离感直达/混响比远场更可能是旁对话
    5语义请求性文本有明确请求对象才像指令

    注意顺序：文本语义排最后，因为 sidetalk 与指令同形（VGBench 的 speaker-switch 就是词完全相同）。

    7.3 数据需求

    类别最小条数说明
    sidetalk500双人/三人 + 快递员/电话等真实打断源；现有中文合成集仅 134 条
    self_talk200自言自语、嘟囔
    user_reject300听不清/噪声掩盖（现有）
    近邻负例每类 1:1同一句话"对系统说 vs 对旁人说"配对，这是最值钱的样本

    数据量用统一公式：N = K × n_min × f_scene × f_neg，语音信道系数取 2.0–3.0，负例系数 2.0。

    7.4 服务化要点

    项建议
    判定位置L1（声学+称呼粗判）→ L2（语义+历史细判），不交给 L3
    静默时的上下文不要直接丢：sidetalk 里常有后续要用的信息（"等会儿提醒我拿快递"）
    持续性旁对话常连续 3–5 轮，需"维持静默"状态机，而不是每轮重判
    重锚旁对话结束后如何接回主线，交给 L3 的转述能力

    8. 评测指标

    8.1 基础三项

    指标定义目标
    拒识率（Rejection Rate）sidetalk 样本中系统保持静默的比例≥90%
    误拒率（False Rejection）真实指令被判成 sidetalk 的比例≤2%（比拒识率更重要）
    静默下的打断率本应静默却开始说话的比例≤3%

    8.2 理由正确性：SMR【论文】

    CoDeTT 的 Semantic Misalignment Rate：拒识对了但理由错了也算错

    （把指令当噪声而静默，与识别出"这是旁对话"而静默，是两件事）。

    自建实现：标注每条样本的"正确理由"（sidetalk / self_talk / noise / backchannel），

    系统输出理由与标注不一致即计 SMR。目标 <10%。

    8.3 产品口径：FAR / FRR 工作点

    F1 高不代表能用。产品要的是在给定误拒预算下的拒识率，因此报告：

    报告项说明
    FRR@FAR=1%误拒 1% 时能拒掉多少 sidetalk
    曲线而非单点与 SAS/VGBench 同类报告方式对齐
    分类别sidetalk / self_talk / speaker-switch 分开报

    8.4 持续性指标（自建，业界空白）

    指标定义
    静默保持率连续 N 轮旁对话中，系统保持静默的轮次比例
    重锚延迟旁对话结束 → 系统重新对主用户发话的间隔

    9. 风险与开放问题

    9.1 风险与对策

    风险说明对策
    复用 reject 态sidetalk 触发澄清话术拆态（§7.1）
    误拒指令把真指令当旁对话，用户认为"没反应"误拒率设 ≤2%，并给"我在听"的低成本反馈
    只靠文本判speaker-switch 场景必然失败引入说话人/历史信号
    单通道硬做F1 上限 ~0.86明确产品边界，或用"轻确认"兜底
    丢弃 sidetalk 内容丢掉后续有用信息静默但入上下文

    9.2 开放问题

    #问题为什么重要
    1单通道手机形态下，历史 + 称呼能把 sidetalk 做到多少无公开数据，直接决定产品形态可行性
    2误拒与误收的代价函数如何定拒错（不回应）与答错（乱答）哪个更伤，决定阈值
    3长时旁对话的边际收益递减点决定状态机维持多久、何时可以忘掉
    4中文真实 sidetalk 数据何时出现决定能否摆脱合成数据的分布偏差
