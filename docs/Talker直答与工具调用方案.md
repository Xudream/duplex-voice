# Talker 直答与工具调用能力设计方案（9B 基线）

> 版本：v1.0 ｜ 日期：2026-10-12
> 范围：Q3 全双工语音项目 Talker 侧 —— 让 Talker 具备「直答 + 简单工具调用」能力
> 模型基线：**9B 级模型**（替代原 4B 基线）
> 关键前提：工具链代码已完整实现，当前处于**配置关闭**状态（`LLM.tools.enabled: false`）

---

## 1. 背景与目标

### 1.1 现状

Talker 目前**只会聊天，不会动手**：

| 能力 | 现状 | 代码位置 |
|---|---|---|
| 直答 | 已有 | `strategy/fast.py` → `providers/fast_llm.py` `answer()` → `modules/llm_planner.py` `plan_stream()` |
| 工具调用 | **代码完整但被关闭** | `modules/tools.py`（ToolEngine / SkillRegistry / MCP）、`core/tool_registry.py` |
| 开关 | `LLM.tools.enabled: false` | `config/model_config.yaml` |
| fast 路径 | 显式屏蔽工具 | `fast_llm.py` `answer()` 内 `enable_tools=False` |

两处关闭点的原始注释（可核对）：

- `system.py`：*"工具代码保留，但配置关闭时不实例化 ToolEngine，避免注册/使用 tools.py 中的 get_weather 等预置工具。需要恢复时只需将 model_config.yaml 的 LLM.tools.enabled 改为 true。"*
- `fast_llm.py`：*"fast 模式只走模型，不读取、注入或调用预置工具。"*

**推论**：此前工具链大概率是**开启后被主动关闭的**（否则不会连 ToolEngine 都不实例化）。因此本方案的核心不是"实现功能"，而是**重新定义边界并防止退化**。

### 1.2 目标

1. Talker 能直答（保持自然对话能力，不退化）
2. Talker 能调用**简单工具**（单/双步、参数扁平、可降级）
3. 明确划分 Talker 与 Thinker 的工具职责，**互不重复**
4. 前台时延不失控（有预算、有兜底、有硬闸门）

### 1.3 非目标

- 不在 Talker 侧做多步任务编排（归 Thinker）
- 不下放有副作用的设备控制类工具（归 Thinker）
- 不为了工具能力牺牲承接语时效性

## 2. 模型基线：为什么选 9B

### 2.1 4B / 9B 能力与成本对比

| 维度 | 4B（原基线） | **9B（本方案基线）** | 设计影响 |
|---|---|---|---|
| 工具调用可靠性 | 勉强，需规则兜底 | 可靠（支持 1–2 步、并行调用） | **可删除大部分规则补偿代码** |
| 直答质量 | 够用 | 明显更好（上下文/情绪/口吻） | 可承担更复杂直答 |
| 首 token 时延（AWQ 4bit，本地 GPU） | 约 120–200ms | **约 250–350ms**（估算） | 承接语预算需重算 |
| 生成速度 | 约 100–150 tok/s | **约 60–90 tok/s**（估算） | 长回复时长增加 |
| 显存（权重） | 约 2.5GB（AWQ） | **约 6–7GB（AWQ）** / 约 18GB（BF16） | 24G 卡用 AWQ 宽裕 |
| 单卡并发 | 高 | 中（AWQ 下可接受） | 需核算 KV cache |

> 标注"估算"的数值须在 P0 阶段实测替换，不得直接作为验收依据。

### 2.2 核心变化

> 4B 时代的设计重心是「**用规则和约束把弱模型撑住**」；
> 9B 时代重心转为「**让模型自己干，同时把时延预算与最大步数卡死**」。

具体表现：规则兜底从主角退为配角，`max_steps` 与 `total_budget` 成为新的主要闸门。

---

## 3. 架构决策：单模型还是双模型

### 3.1 方案对比

9B 变慢后，最直接的冲突点是**承接语首字**（前台最敏感指标）。

| 方案 | 承接语首字 | 显存/运维 | 复杂度 |
|---|---|---|---|
| **A. 9B 单模型全包**（承接语 + 直答 + 工具） | 约 350ms | 一套 | 低 ✅ |
| B. 4B 承接语 + 9B 直答/工具 | 约 200ms | 两套（双预热/双运维） | 高 |

### 3.2 决策

**采用方案 A**，理由：

1. 承接语首字 200ms → 350ms 的增量仍在预算内，**不值得为 150ms 引入第二套模型的运维复杂度**
2. 9B 生成的承接语更自然，减少"答非所问"
3. 单模型避免"两个模型口径不一致"的新缺陷

### 3.3 回退条件

仅当 P0 实测发现首字超出预算（>600ms），才启用方案 B（保留 4B 作为承接语旁路）。

## 4. 能力边界与三级路由

### 4.1 路由结构

```
                   用户 query（ASR 定稿 + 语义 VAD = speak）
                                │
                    ┌───── 路由判据 ─────┐
                    │ 规则预筛 → 9B 预判  │  ← 复用 fast_llm.predict_route()
                    └─────┬──────────────┘
        ┌─────────────┬───┴──────────┬──────────────────┐
        ▼             ▼              ▼                  ▼
     直答路径      本地工具路径    上交 Thinker        丢弃
   （无外部依赖）  （单/双步）    （多步·业务系统·    （附和/噪声）
                                  需 Skill/超预算）
```

对应现有策略类：`strategy/fast.py`（直答）、新增或复用工具策略、`strategy/direct.py`（Thinker 正文直出）。

### 4.2 判据必须可计算

不使用"看情况"式描述，全部落为可判定条件：

| 路由 | 硬判据 |
|---|---|
| 直答 | 无需外部信息且无需动作（闲聊、常识、追问澄清） |
| 本地工具 | 命中白名单 ∧ 参数单层 ∧ 预计 < 1.5s ∧ 工具标记 `owner: talker` |
| 上交 Thinker | 步数 > `max_steps` ∧ 需业务系统 ∧ 工具标记 `owner: thinker` ∧ 前两条超预算 |

### 4.3 关键设计：Talker 与 Thinker 工具集互斥

这是双通道架构最容易出问题的点：同一个能力两边都能做 → 路由抖动、行为不一致、日志难排查。

**做法**：每个工具/技能注册时打 `owner` 标签：

```yaml
tools:
  - name: get_current_time
    owner: talker        # 本地快路径
  - name: search_web
    owner: thinker       # 远端慢路径
```

启动时校验：若同名工具在两侧同时注册，**启动失败并报错**（而非运行期静默择一）。

### 4.4 路由实例（用于测试集构造）

| 用户输入 | 路由 | 理由 |
|---|---|---|
| "现在几点了" | 本地工具 | 命中 `get_current_time`，参数为空 |
| "明天上海天气怎么样" | 本地工具 | 命中 `get_weather`，单层参数 |
| "帮我设个明早 8 点的提醒" | 本地工具（L2，需确认） | 写操作，可逆 |
| "帮我看看这周还有哪些会议" | 上交 Thinker | 需业务系统 |
| "先查天气，如果下雨就把提醒改成带伞" | 上交 Thinker | 条件分支，步数不可控 |
| "嗯嗯" / "对" | 丢弃 | backchannel，语义 VAD 判 idle |
| "你觉得这个设计怎么样" | 直答 | 无外部依赖 |

## 5. 直答路径设计

### 5.1 保持骨架不动

```
FastStrategy.generate()            # strategy/fast.py
  └─ fast_provider.answer(enable_tools=False)   # providers/fast_llm.py
      └─ planner.plan_stream(...)               # modules/llm_planner.py
          └─ SystemPrompt 人设 + 情绪上下文 + 滑动历史 + delta 流式
```

9B 接入即可获得质量增益，**无需改结构**。失败兜底沿用现有的 `default_transition()` + "暂时没能理解您的问题"逻辑。

### 5.2 9B 下需要新增的三项约束

| 项 | 原因 | 落点 |
|---|---|---|
| 回复长度硬约束 | 9B 更能说 → 回复变长 → TTS 时长增加，语音体验变差 | SystemPrompt 增加"口语化，1–2 句" |
| 上下文窗口放宽 | 9B 支持更长历史，直答连贯性提升 | 滑动窗口 3 轮 → 6–8 轮 |
| 长度埋点 | 观察"说说变长"是否真实发生 | `core/latency.py` 增加输出 token 数统计 |

### 5.3 示例

用户："今天有点累"
- 9B 直答（1–2 句）："听起来挺辛苦的，要不要先歇会儿？" → 约 15 字，TTS 约 2s
- 若不加长度约束，9B 可能输出 80–120 字 → TTS 约 10s，全双工体验直接崩坏

> 这条约束在语音场景中是**硬性**的，不是风格偏好。

## 6. 工具调用路径设计

### 6.1 执行流程（9B 支持双步）

```
① 路由判定命中「本地工具」
② LLM(tools=白名单, tool_choice="auto", guided JSON)   ← enable_tools=True
③ 解析 tool_calls
   ├─ 无 → 按直答处理（模型自答）
   └─ 有 → ④ 权限校验：owner=talker ∧ 参数 schema ∧ 风险级
⑤ 并行/串行执行 execute_tool()（带 timeout）
⑥ ToolResult 回灌 messages
   └─ 若需第 2 步 → 重复 ②~⑤（*第 2 步起必须已有长承接语覆盖*）
⑦ 最终总结流式播报
```

### 6.2 工具风险分级

| 级别 | 工具 | Talker 可否直接执行 | 处理方式 |
|---|---|---|---|
| L0 只读·本地 | `get_current_time` | ✅ 直接 | 无需确认 |
| L1 只读·外部 | `get_weather` | ✅ 直接 | 带 timeout，失败即降级 |
| L2 写·可逆 | `set_reminder` | ⚠️ 需确认 | 先播报"帮你设 8 点提醒，可以吗？"，待确认后执行 |
| L3 有副作用 | `control_device`、`play_music` | ❌ 归 Thinker | 本地不执行 |

**分级判据唯一**：做错了能否一句话撤回。不能撤回的一律上交。

### 6.3 9B 后可删除的补偿代码

| 原补偿手段 | 9B 版处理 |
|---|---|
| 100+ 城市硬编码白名单（`llm_planner.py` `CHINESE_CITIES`） | **删除**，改由模型抽取 + schema 校验 |
| `re.search(r'我叫([^\s，。！？]+)')` 正则 | **删除**，模型直接抽参 |
| `max_steps = 1` 硬限制 | **放宽到 2** |
| 串行工具调用 | **支持并行**（`parallel_tools`） |
| 工具描述粗糙 | **仍需精写**（9B 也吃描述质量） |

> 该项是本方案最直接的降本体现：**规则代码行数目标下降 >80%**。

### 6.4 中断与取消（全双工特有）

工具执行是异步的，用户随时可能插话，规则如下：

| 场景 | 处理 |
|---|---|
| 工具执行期间用户插话 | 立即 cancel 工具任务 + 丢弃结果（复用现有 `GenerationCancelled`） |
| L2 已确认的写操作进行中插话 | **不撤回**（用户已确认却被撤销会造成语义混乱），仅停止播报 |
| 播报工具结果时被插话 | 沿用现有 barge-in 逻辑 |

## 7. 时延预算（9B 版）

### 7.1 时间轴

Talker 是前台，其硬约束是"嘴不能停"。因此工具路径必须挂在预算上：

```
T0  ASR 定稿 / 语义 VAD = speak
│
├── 0 ~ 350ms      路由预判（9B 预判 / 规则快速路径）
├── 0 ~ 600ms      承接语首字出声
│                  （= 9B 首 token 250–350ms + 短文本生成）
├── 600ms ~ 3.2s   工具窗口（较 4B 版放宽 0.7s）
│      ├─ 工具决策（9B 带 tools）      约 400–600ms
│      ├─ 工具执行                      timeout 1.5s
│      └─ 结果总结（9B 流式）           首 token 350ms，边生成边播
└── > 3.2s        强制上交 Thinker + 长承接语（复用 LONG_WAIT 变体）
```

### 7.2 与 4B 版的预算对比

| 环节 | 4B 版 | **9B 版** | 变化 |
|---|---|---|---|
| 承接语首字 | ≤ 800ms | ≤ 600ms（目标） | 实际会更接近上限 |
| 工具窗口 | 0.8–2.5s | 0.6–3.2s | 放宽 0.7s |
| 总预算 | 2.5s | **3.2s** | 放宽 0.7s |
| 最大步数 | 1 | **2** | 放宽 |

### 7.3 配置模板

```yaml
LLM:
  model: "<9B 模型路径>"
  tools:
    enabled: true
    talker_allow: [get_current_time, get_weather, set_reminder]
    tool_timeout_ms: 1500
    total_budget_ms: 3200          # 4B 版为 2500
    max_steps: 2                   # 4B 版为 1
    parallel_tools: true           # 9B 支持并行工具调用
    require_confirm: [set_reminder]
    json_schema_enforced: true     # 保留：作防御而非兜底
```

### 7.4 兜底策略

| 失败点 | 降级动作 |
|---|---|
| 工具执行超时（>1.5s） | 放弃本地，转 Thinker，或播报"我查一下，稍等" |
| 模型决策超时（>600ms） | 降级为直答 |
| 总预算耗尽（>3.2s） | 强制上交 Thinker + 长承接语 |
| 工具执行异常 | 播报通用失败话术，绝不透出原始错误 |

**建议**：每次工具调用**同时预生成慢通道问题**（与现有快慢融合一致）——若工具失败，用户已在听承接语，感知上无空档。

## 8. 部署配置

### 8.1 vLLM 启动参数

```bash
vllm serve <9B模型路径> \
  --served-model-name qwen-9b-talker \
  --quantization awq_marlin \          # 24G 卡推荐 4bit；40G+ 可上 bf16
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85 \      # 留 15% 给 KV cache 波动
  --enable-auto-tool-choice \          # 必须，否则 tools= 不生效
  --tool-call-parser hermes \          # Qwen 系列常用；须按实际模型验证
  --guided-decoding-backend xgrammar \ # JSON schema 硬约束
  --disable-log-requests
```

**关键前置**：`--tool-call-parser` 必须与实际模型的输出格式匹配。建议在 P1 之前用 5 条固定 query 做单测，不要等到联调才发现格式对不上。

### 8.2 显存预算（24G 卡，AWQ 4bit）

```
权重           约 6–7 GB
KV cache       约 8–10 GB（8192 ctx × 并发 4–6）
激活/开销      约 2 GB
──────────────────────────
合计           约 17–19 GB / 24 GB   ✅ 有余量
```

若为 16G 卡：降 `max-model-len` 至 4096 + 并发 2–3，或改用 GPTQ-int4。

### 8.3 连接与预热

- 现有 `LOCAL_LLM_BASE_URL`（容器内指向推理服务）与 `LOCAL_LLM_MODEL` 需同步更新为 9B
- 现有 `prewarm_transition()` 预热机制保留，但**预热耗时随模型变大而增加**，需复核启动超时配置

## 9. 安全设计

模型变强**不等于可以放松防御**。9B 更"能说会道"，意味着一句话说得更合理，**误触发的后果反而更隐蔽**。

### 9.1 五道防线

| # | 防线 | 说明 | 9B 下是否保留 |
|---|---|---|---|
| 1 | 白名单制 | 仅注册 `owner: talker` 的工具对模型可见 | 保留 |
| 2 | 参数 schema 强校验 | 拒绝超范围/超长/非法值，防 prompt 注入进入工具参数 | 保留 |
| 3 | L2 写操作二次确认 | 播报确认后再执行 | 保留 |
| 4 | L3 一律上交 Thinker | 不因模型变强而下放设备控制 | 保留 |
| 5 | 审计日志 | 谁/何时/调了什么/参数/结果/耗时，可回放 | 保留 |

### 9.2 唯一可精简的部分

原为 4B 编写的关键词与正则兜底，9B 下**可以删除**——删除后反而减少误判（规则与模型判断冲突时，规则通常是错的一方）。

## 10. 可观测性

### 10.1 埋点清单

| 埋点 | 位置 | 用途 |
|---|---|---|
| 各阶段时延 | `core/latency.py`（已有） | 验证时延预算是否达线 |
| 路由决策结果与理由 | 路由判据出口 | 排查"为什么走了这条" |
| 工具调用链路 | `execute_tool` 前后 | 工具名/参数/耗时/成败 |
| 降级次数与原因 | 各兜底分支 | 评估系统稳定性 |
| 输出 token 数 | 直答完成时 | 监控"回复变长" |
| 误触发样本采集 | 负例集命中时 | 持续优化测试集 |

## 11. 分阶段落地

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| **P0 基线压测** | 9B 单模型接入，**先不开工具**，只验直答 | 直答首字 P95 ≤ 600ms；确认单模型方案可行（否则启用方案 B） |
| **P1 只读单步** | 开 `tools.enabled`，白名单 `get_current_time` + `get_weather`，`max_steps=1` | 误触发 <3%，参数准确 >97%，P95 ≤ 3.2s |
| **P2 双步 + 写操作** | `max_steps=2` + `set_reminder` + 确认流程 | 双步链路稳定；确认流程可打断不出错 |
| **P3 并行 + 删规则** | `parallel_tools=true`；删除城市白名单与正则兜底 | 删规则后准确率不下降 |
| **P4 MCP 扩展** | 动态工具发现 + owner 冲突校验 | 新增工具无需改代码 |

### 11.1 为什么 P0 是新增的关键一步

9B 换模型本身自带风险（首字、并发、tool parser 是否匹配）。把"换模型"和"开工具"两件事**分开验证**，否则一旦指标不达标，无法判断是模型问题还是工具链路问题。

### 11.2 P1 是最大价值验证点

P1 能最快回答关键问题：**9B 到底还需不需要规则兜底**。若 P1 达标，P3 的删规则就是纯收益；若不达标，则应先排查 tool parser 与 prompt，而非直接再升模型。

## 12. 验证方案

### 12.1 指标体系（9B 版阈值）

| 指标 | 4B 版目标 | **9B 版目标** | 取数方式 |
|---|---|---|---|
| 工具选择准确率 | >95% | **>97%** | 测试集正例 |
| 误触发率 | <5% | **<3%** | 测试集负例 |
| 参数准确率 | >95% | **>97%** | 参数逐项比对 |
| 直答首字 P95 | ≤800ms | **≤600ms** | `core/latency.py` |
| 工具段 P95 | ≤1.5s | ≤1.5s | 同上 |
| 端到端 P95 | ≤2.5s | **≤3.2s** | 同上 |
| 规则兜底代码行数 | — | **下降 >80%** | 代码统计 |

### 12.2 测试集构造

**正例（应触发工具）**，按工具分类：
- `get_current_time`："现在几点" / "今天几号" / "今天星期几"
- `get_weather`："明天上海天气" / "北京冷不冷" / "杭州要带伞吗"
- `set_reminder`："明早 8 点提醒我开会" / "半小时后叫我"

**负例（不应触发工具）** —— **这是重点**：
- 闲聊："今天心情不错"
- backchannel："嗯嗯" / "对" / "好的"
- 语义相似但不需工具："你说现在几点比较合适出发"（讨论，非查询）
- 需求模糊："帮我弄一下"（应追问而非乱调工具）

> 这类功能最常见的失败不是"调不对"，而是"**不该调的时候乱调**"。负例集应占测试集一半以上。

### 12.3 P3 双跑对比

删除规则兜底前，保留一天**双跑对比**（规则版 vs 纯模型版），以数据确认删除安全，而非凭信心删除。

## 13. 风险与应对

### 13.1 风险清单与缓解措施

| 风险 | 影响 | 应对 |
|---|---|---|
| 首字退化（9B 慢约 150ms） | 承接语时效性下降 | P0 先量；超预算即启用方案 B（4B 承接语旁路） |
| 显存不足以开并发 | 多人使用时排队 | AWQ/GPTQ-int4；降 `max-model-len`；或换更大卡 |
| tool parser 不匹配 | 工具调用完全不可用 | P1 前先用 5 条固定 query 单测 parser |
| 9B 回复变长 | TTS 时长增加，体验崩坏 | prompt 硬约束"1–2 句口语化" |
| 删规则后出现新误判类型 | 准确率回退 | P3 双跑对比；保留回滚开关 |
| 与 Thinker 职责重叠 | 路由抖动、行为不一致 | `owner` 标签互斥 + 启动期冲突校验 |
| 危险操作误触发 | 副作用不可逆 | L3 一律上交；L2 二次确认 |
| 此前工具链正是因不稳被关闭 | 重蹈覆辙 | P1 仅开只读单步，用数据决定是否继续 |
